2. 1번에서 우리의 목표를 달성하려면 어떤내용의 데이타를 어떻게 DB에 저장하고 또 그 저장된 내용을 어떻게 해야 정확한 사주풀이를 할수있는지 알려줄수있나요?


1. 지금 고객 사주와 Gemini 결과를 DB에 저장하는 의미가 있나요?

네, 의미가 큽니다. 하지만 Gemini가 작성한 문장만 계속 쌓는 것만으로는 자체 사주풀이 엔진을 만들기 어렵습니다.

현재 저장 데이터는 다음 용도로 가치가 있습니다.

같은 사주총평을 다시 볼 때 Gemini를 호출하지 않는 캐시
Gemini 모델·프롬프트 버전별 결과 비교
잘된 풀이와 잘못된 풀이를 검수하는 자료
나중에 자체 규칙과 풀이 문장을 만드는 참고 데이터
고객 피드백과 전문가 수정을 연결하는 기반
API 비용과 로딩 시간 절감

현재 saju_interpretations에 저장하는 다음 항목들은 좋은 시작입니다.

saju_chart_id
interpretation_type
period_key
structured_result
content
model_name
prompt_version
engine_version
input_snapshot
quality_status
user_consent_for_improvement

다만 중요한 점은 DB는 데이터를 보관할 뿐, DB 자체가 사주를 풀이해 주지는 않는다는 것입니다. Gemini를 완전히 사용하지 않으려면 별도의 명리 규칙 엔진과 검수된 풀이 문장 데이터가 필요합니다.

2. 자체 사주풀이를 위해 무엇을 저장해야 하나요?

크게 세 종류를 분리해서 저장해야 합니다.

A. 만세력 사실 데이터

이 부분은 Gemini가 판단하면 안 되고, 우리 만세력 계산 엔진이 확정해야 합니다.

저장 내용	예시
사주 원국	년주·월주·일주·시주
일간 정보	일간, 오행, 음양
계절 정보	월지, 절기, 조후
오행 분포	목·화·토·금·수 개수와 가중치
십성 분포	비견·겁재·식신·상관·재성·관성·인성
지장간	각 지지의 본기·중기·여기
관계 정보	합·충·형·파·해·삼합·방합
신강·신약	판정값, 점수, 판정 근거
격국	격국명, 성립 근거, 예외 조건
용신·희신	선정 결과와 선정 근거
대운	시작 나이, 각 대운 간지, 작용 관계
계산 버전	어떤 계산 로직으로 산출했는지

권장 신규 테이블은 saju_feature_snapshots입니다.

saju_feature_snapshots
- id
- saju_chart_id
- feature_version
- day_master
- season
- five_elements_json
- ten_gods_json
- relations_json
- strength_json
- structure_json
- useful_elements_json
- daeun_json
- feature_hash

feature_hash가 같으면 이름이나 생년월일을 노출하지 않고도 동일한 명리 구조의 결과를 재사용할 수 있습니다.

B. 명리학 풀이 규칙

이것이 나중에 Gemini를 대신할 핵심 자산입니다.

예를 들면 다음과 같은 규칙입니다.

월령에서 일간을 돕고 인성이 강하며 관성이 적절한 경우
→ 신중함, 학습력, 책임감이 강하게 표현될 가능성이 높다.

권장 테이블:

myeongri_rules
- id
- rule_code
- category
- school
- condition_json
- priority
- conflict_group
- conclusion_json
- rationale
- source
- rule_version
- review_status
- reviewed_by

여기서 condition_json에는 규칙이 성립하는 조건을 저장합니다.

{
  "all": [
    { "feature": "day_master.element", "equals": "土" },
    { "feature": "strength.class", "in": ["중화", "신강"] },
    { "feature": "ten_gods.정관", "greaterThan": 0 }
  ]
}

반드시 school과 rule_version을 저장해야 합니다. 신강·신약, 격국, 용희신은 명리학 유파마다 판단이 달라질 수 있기 때문에 여러 방식의 규칙을 무분별하게 섞으면 풀이가 서로 모순됩니다.

C. 검수된 풀이 문장

명리 규칙만으로는 사용자에게 읽기 좋은 긴 문장을 만들기 어렵습니다. 각 규칙과 연결된 자체 풀이 문장을 준비해야 합니다.

interpretation_blocks
- id
- rule_code
- section_code
- headline
- body
- advice
- tone
- locale
- block_version
- review_status

예를 들어 같은 규칙이라도 다음 섹션마다 풀이 문장이 달라집니다.

한눈에 보는 나의 사주
타고난 성격과 기질
강점과 가능성
인간관계
직업 성향
재물 성향
연애 성향
인생의 성장 흐름
자체 풀이가 만들어지는 과정

이 구조가 완성되면 Gemini 없이도 같은 만세력에는 같은 근거를 바탕으로 일관된 풀이가 나옵니다.

가장 현실적인 개발 단계
1단계: 현재 방식 유지

현재처럼 Gemini가 풀이하고 결과를 DB에 저장합니다.

다만 앞으로는 결과 문장뿐 아니라 다음 정보도 같이 저장하는 것이 좋습니다.

{
  "facts_used": [],
  "rules_used": [],
  "gemini_result": {},
  "expert_corrected_result": null,
  "review_status": "unreviewed"
}
2단계: 자체 명리 규칙 + Gemini 문장화

우리 엔진이 다음을 먼저 확정합니다.

신강·신약
오행 균형
핵심 십성
합충형파해
격국
용희신
대운의 주요 작용

Gemini에는 계산을 맡기지 않고, 확정된 사실과 규칙을 자연스러운 문장으로 풀어쓰는 일만 맡깁니다. 이 단계가 정확도와 개발 비용의 균형이 가장 좋습니다.

3단계: Gemini 제거

검수된 interpretation_blocks가 충분히 쌓이면 자체 조합기가 규칙별 문장을 선택하고 연결합니다.

자연스러운 문장 연결이 더 필요하면 외부 Gemini 대신 자체 서버에서 실행하는 소형 언어모델을 사용할 수도 있습니다. 다만 계산과 핵심 판정은 계속 규칙 엔진이 담당해야 합니다.

고객 데이터 사용 시 중요한 기준

Gemini 결과를 곧바로 학습 정답으로 사용하면 안 됩니다. Gemini도 명리적 오류나 모순을 만들 수 있기 때문입니다.

데이터를 다음과 같이 구분해야 합니다.

unreviewed: Gemini가 생성했지만 아직 검수되지 않음
approved: 전문가가 내용과 근거를 확인함
corrected: 전문가가 수정함
rejected: 오류 또는 모순이 있어 학습에서 제외함

또한 고객의 이름과 생년월일을 학습 데이터에 직접 넣지 않고, 익명화된 chart_hash와 명리 특징만 사용해야 합니다. 현재 코드에 있는 user_consent_for_improvement와 is_training_approved 필드는 바로 이 목적으로 잘 만들어져 있습니다.

결론

현재 저장 작업은 헛된 작업이 아닙니다. 캐시와 품질 검수 자료로 매우 중요합니다. 다만 장기적으로 자체 풀이를 만들려면 다음 세 가지가 추가돼야 합니다.

계산된 명리 특징 데이터
전문가가 검수한 명리 규칙
규칙별 자체 풀이 문장

가장 좋은 다음 작업은 사주총평 2번을 바로 생성하기 전에, 먼저 saju_feature_snapshots 구조를 설계하여 Gemini가 어떤 만세력 사실을 근거로 풀이했는지 함께 저장하는 것입니다. 이렇게 해야 지금 만드는 12가지 사주총평이 나중에 자체 풀이 엔진의 실제 자산으로 남습니다.
